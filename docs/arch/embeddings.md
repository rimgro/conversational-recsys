# Эмбеддинги треков: откуда берутся и как учатся

Трек в обеих башнях (v1, v2, lazy) описывается только **содержанием** — без обучаемого вектора на ID трека. Источников
три:

| источник | что описывает | где строится | в каких моделях |
|---|---|---|---|
| **коды RQ-VAE** (semantic ID) | звучание | заранее: MuQ → RQ-VAE → 4 числа | v1, v2, lazy |
| **теги** Last.fm + жанры | жанр, настроение, эпоху (как люди описывают трек) | обучаемая таблица тегов | v2, lazy |
| **название** «артист — название» | что Qwen знает об артисте и песне | заранее: Qwen3-Embedding, заморожен | lazy |

Схема: `docs/figures/embeddings.svg`.

## 1. Коды RQ-VAE (semantic ID)

### 1.1. Вход: MuQ

Каждый трек каталога имеет `muq_embedding` — **аудио-эмбеддинг MuQ** (самообучаемая модель музыкального аудио),
128 чисел, L2-нормирован. Он дан в `tracks_meta`, сами мы MuQ не запускали. Описывает только звук: не текст, не теги,
не прослушивания.

### 1.2. RQ-VAE: 128 чисел → 3 кода

RQ-VAE (Residual-Quantized VAE, как в TIGER / «Recommender Systems with Generative Retrieval») обучен в DataSphere
(`tiger_larger_outputs`). Код обучения в репозитории не лежит, есть чекпоинт `artifacts/semantic_ids/rqvae_checkpoint.pt`
и его конфиг: 10 эпох, batch 128, 3 уровня, кодбук 256, латент 32.

```
энкодер:      MuQ [128] → Linear 128→128 → ReLU → Linear 128→32 → ReLU → Linear 32→32 (без bias) = z  [32]

квантование (3 уровня, у каждого свой кодбук 256 × 32):
              остаток₀ = z
              c_k = argmin_c ‖остаток_{k-1} − кодбук_k[c]‖       (ближайший центроид, евклидово)
              остаток_k = остаток_{k-1} − кодбук_k[c_k]
              ẑ = кодбук₁[c₁] + кодбук₂[c₂] + кодбук₃[c₃]         ≈ z, ошибка ~22% нормы z

декодер:      ẑ [32] → 32 → ReLU → 128 → ReLU → 128   (восстанавливает MuQ; нужен только при обучении RQ-VAE)
```

**Смысл:** первый код — грубый кластер звучания, второй уточняет остаток, третий — ещё тоньше. Похожие по звуку треки
получают общий префикс кода. Лосс по устройству модели — стандартный для RQ-VAE: реконструкция MuQ + commitment
к центроидам. Но код обучения в репозитории не лежит, так что это **не проверено**.

**4-я позиция.** Три кода общие с другим треком у 7.8% треков (4 988). Поэтому добавлено 4-е число 0..8 — номер
трека среди треков с тем же тройным кодом (почти всегда 0). С ним коллизий нет. Больше половины коллизий — другие
записи той же песни, звук у них одинаковый.

**Проверено** (`scripts/check_semantic_ids.py`): чекпоинт по MuQ воспроизводит 100% кодов; все 256 значений каждого
уровня используются, треки распределены ровно (медиана ~245 треков на значение).

Итог: `semantic_codes.npy`, (64 016 × 4), словарь позиций `[256, 256, 256, 9]` = 777 строк в таблицах.

### 1.3. Как коды становятся обучаемыми эмбеддингами

Сами коды — номера, а векторы для них учатся вместе с башнями. **Центроиды RQ-VAE используются как старт**, чтобы
похожие по звуку треки с первого шага были рядом. Ablation `codes.init=random` проверяет, нужно ли это.

**v1 — башня трека** (`ItemTower`): таблица 777 × 32, строки инициализированы **самими центроидами** (у 4-й позиции —
нули). Сумма 4 строк на старте = ẑ, квантованный вектор RQ-VAE. Дальше MLP 32→256→256 → L2. Таблица учится.

**v1 / v2 — токены на входе Qwen** (`SemanticTokenEmbedding`), размерность 1024:
```
E[k, c] = P · центроид_k[c]  +  Δ[k, c]  +  level_emb[k]
```
- `P` — Linear 32→1024, **одна на все строки**. Масштаб подобран так, чтобы средняя норма `E` совпала со средней нормой
  обычных токенов Qwen. Иначе токены треков на старте заглушили бы текст или утонули в нём.
- `Δ` — своя поправка каждой строке, старт с нуля (у 4-й позиции, где центроида нет, — случайный шум той же нормы).
- `level_emb` — какая это позиция кода (1, 2, 3 или 4-я).

На старте токен = проекция центроида. Обучение двигает и общую `P`, и поправки строк.

**v2 — общая таблица.** Та же `E` используется и в башне трека: среднее 4 строк → Linear 1024→256 → LayerNorm. Один
трек описывается одними параметрами и как токен истории, и как кандидат.

**lazy** — своя таблица 777 × 32 (старт — центроиды, у 4-й позиции — шум с нормой центроидов), 4 строки
**склеиваются** в 128 и идут в MLP 128→256→256.

## 2. Теги (`recsys/twotower/tags.py`, `TagTable`)

**Словарь.** Теги Last.fm трека (с весами 0..100) и жанры каталога. Одинаковые названия тега и жанра — один элемент.
В словарь попадает тег, который есть хотя бы у 5 треков, — получается ~12.5k элементов. Элемент 0 — `<no_tags>` для
треков без тегов из словаря.

**Веса трека.** Вес тега = вес Last.fm / 100, вес жанра = 0.5 (если тег совпадает с жанром, веса складываются). У трека
остаются до 32 тегов с наибольшим весом, и веса **нормируются на сумму 1**, чтобы вектор не зависел от числа тегов.

**Эмбеддинг.** Обучаемая таблица ~12.5k × 256 (старт — N(0, 1/256), без предобучения):
```
вектор тегов трека = Σ_i w_i · T[тег_i]          (embedding_bag, mode=sum)          [256]
```
Учится целиком из лосса two-tower. В v2 таблица общая: она входит в башню трека и, через `Linear 256→1024` со стартом
из нулей, добавляется к токенам истории на входе Qwen. Это самая большая обучаемая часть v2 (~3.2M параметров).

## 3. Название трека (только lazy)

`scripts/encode_item_text.py`: строка `«m4a_artist — m4a_song»` → **Qwen3-Embedding-0.6B** (та же модель, что в
башне пользователя) → скрытое состояние EOS → L2 → вектор 1024 (float16, `artifacts/item_text/qwen3emb.npz`).
Без инструкции: так в Qwen3-Embedding кодируются документы (запросы кодируются с инструкцией). Считается **один раз
заранее**: на каждом шаге обучения нужны векторы всех 64k треков, и прогонять через Qwen весь каталог на каждом шаге
невозможно. Векторы заморожены, обучается только `Linear 1024→256 → LayerNorm` поверх.

## 4. Как всё это учится вместе

Отдельного предобучения эмбеддингов (кроме RQ-VAE и Qwen) нет: таблицы кодов, тегов и проекции учатся **end-to-end
из лосса two-tower**, то есть softmax по всем 64 016 трекам:

- на каждом шаге башня трека считает `r` и `v` **для всего каталога** (это дёшево: MLP на 64k строк);
- логиты `u · v / τ` для всех треков, cross-entropy с целевым треком, другие записи той же песни замаскированы;
- градиент идёт во все таблицы: через `v` цели и всех негативов, а в v2 / lazy ещё через токены истории.

Этап A (Qwen заморожен) — фактически обучение эмбеддингов треков и проекций под замороженный Qwen. Этап B
добавляет LoRA, и Qwen подстраивается под новые токены.

Почему без ID-эмбеддинга: у большинства треков мало взаимодействий, их ID-вектор был бы шумом. Векторы из
содержания обобщаются на редкие и новые треки: похожий звук и теги дают похожий вектор.
