# Two-tower v2 (и v1): история в промпте Qwen

Кандген `twotower`, код — `recsys/twotower/model.py` (`TwoTowerV2`, `UserTowerV2`, `SharedItemTower`),
конфиг — `configs/twotower.yaml` (`arch: v2`). Схемы: `docs/figures/twotower_v2.svg`, `docs/figures/twotower_v1.svg`.
Как получены эмбеддинги треков (MuQ → RQ-VAE → коды, теги) — [embeddings.md](embeddings.md).

## Задача и общая идея

Запрос пользователя (текст реплики) + его история прослушиваний → один трек из каталога 64 016 треков.
Модель — две башни, которые отображают в одно пространство размерности 256:

- **башня пользователя**: (история, текст запроса) → `u` ∈ R²⁵⁶, ‖u‖ = 1;
- **башня трека**: трек → `v` ∈ R²⁵⁶, ‖v‖ = 1;
- **скор** = `u · v / τ`, τ обучается (старт 0.05, не меньше 0.01).

На инференсе векторы всех треков считаются один раз, а для запроса берутся top-K ближайших по скалярному
произведению. Поэтому это кандген: он быстро сужает 64k треков до сотен, а дальше их ранжирует CatBoost.

## Башня трека

Трек описывается **только содержанием**: 4 кода RQ-VAE (звук) и теги. Отдельного обучаемого вектора на ID трека нет,
поэтому у редких треков вектор не получается шумным.

```
коды c1, c2, c3 ∈ 0..255, c4 ∈ 0..8
   → строки общей таблицы кодов E (SemanticTokenEmbedding, 777 строк × 1024)
   → среднее 4 строк → Linear 1024→256 → LayerNorm                         [256]
теги трека (до 32 шт., веса в сумме 1)
   → взвешенная сумма строк таблицы тегов T (TagTable, ~12.5k × 256)
   → LayerNorm                                                               [256]
склейка                                                                      [512]
   → MLP: Linear 512→512 → GELU → Linear 512→256                        = r_j  [256]
   → Linear 256→256 → L2-нормировка                                       = v_j  [256]
```

`r_j` — внутреннее представление трека, `v_j` — вектор-кандидат. Оба нужны и в башне пользователя (см. «короткий путь»).

## Башня пользователя

### Вход Qwen

Основа — **Qwen3-Embedding-0.6B**: 28 слоёв, hidden 1024, 16 голов q / 8 голов k-v по 128 (GQA). Вход — одна
последовательность (паддинг слева):

```
Instruct: Given a user's listening history and a request, retrieve the music track the user wants
Query: History: [t1: 4 токена] [t2: 4 токена] … [t64: 4 токена] Request: <текст запроса> <EOS>
```

- **Текстовые токены** — родной (замороженный) эмбеддер Qwen.
- **История** — последние 64 *уникальных* трека пользователя, от старых к новым. Каждый трек — **4 «токена»**,
  по одному на позицию кода. Это не слова словаря Qwen, а векторы размерности 1024, которые подставляются через
  `inputs_embeds`:

  ```
  токен (трек j, позиция k) = E[k, c_k(j)] + Linear 256→1024 (теги трека j)
  E[k, c] = P · центроид_k[c]  +  Δ[k, c]  +  level_emb[k]
            ↑ 32→1024, общая       ↑ своя поправка   ↑ «какая это позиция кода»
  ```
  Подробно про инициализацию — в [embeddings.md](embeddings.md). Linear для тегов стартует с нулей: в начале обучения
  токены такие же, как в v1, а теги подмешиваются постепенно.
- Запрос обрезается до 96 токенов. При 64 треках история занимает 256 токенов, весь вход — ~300–350 токенов.

Выход — скрытое состояние последнего токена (EOS): `h` ∈ R¹⁰²⁴. Так Qwen3-Embedding пулит и в оригинале.

### Голова и «короткий путь» из истории

```
основной путь:   Linear 1024→256 (h)

короткий путь:   q = Linear 1024→256 (h)
                 ключи   k_j = Linear 256→256 (r_j)  по трекам истории (по одному на трек)
                 значения     = v_j — сами векторы-кандидаты этих треков
                 + пустой слот: ключ null_key, значение null_val («ничего из истории»)
                 a = softmax( q·k_j / √256 ; q·null_key / √256 )
                 прочитанное = Σ_j a_j · v_j + a_пусто · null_val

u = L2( Linear(h) + α · прочитанное ),    α обучается (старт 1)
```

Зачем короткий путь: в v1 трек, который модель видела во входе, попадал в её top-200 только в 41% случаев. Если запрос
про трек из истории («включи ту песню…»), attention даёт ему большой вес `a_j`, и `u` сдвигается **прямо к его `v_j`**,
минуя 28 слоёв Qwen. Значения — именно `v_j`, а не проекция «с нуля»: иначе на старте чтение было бы шумом, и
модель научилась бы просто выключать его пустым слотом. Пустой слот нужен для запросов «хочу новое» и для пустой
истории. Его средний вес пишется в лог («пусто»).

### Общие веса башен

Таблица кодов `E` и таблица тегов `T` — **одни и те же параметры** на входе Qwen (токены истории) и в башне трека
(кандидат). Поэтому трек в истории и тот же трек-кандидат описываются одинаково, и градиенты от обеих ролей
обучают одну таблицу.

## Обучение

**Данные.** Пример = (история пользователя на момент запроса, текст запроса, целевой трек). Учимся на всём train
(`twotower.train.part: train`), валидация — 5% пользователей части `index` целиком (по хешу `user_id`).

**Аугментация истории.** В половине примеров (`history_dropout: 0.5`) история обрезается до случайной длины 0..64.
Поэтому модель работает и при короткой, и при пустой истории, а ablation по длине истории делается на одной модели
без переобучения.

**Лосс — softmax по всему каталогу.** На каждом шаге считаются `v` всех 64 016 треков, логиты `u · V / τ` — это
матрица (B × 64016), дальше cross-entropy с меткой = цель. Негативы — все остальные треки.
- **Маска дублей:** другие записи той же песни (общий ISRC или одинаковые «артист — название», 9.2% треков) — не
  негативы, у них логит −∞. Иначе модель штрафовали бы за правильный по смыслу ответ.
- Альтернатива для ablation: `in_batch`-негативы (цели других примеров батча) + logQ-поправка на популярность.

**Два этапа:**

| этап | эпох | что учится | lr |
|---|---|---|---|
| A | 0.3 | таблицы кодов и тегов, проекции, башня трека, короткий путь, τ. **Qwen заморожен** | 1e-3 |
| B | 1.7 | всё то же + **LoRA** r=16, α=32 на q, k, v, o всех 28 слоёв Qwen | 5e-4; LoRA 2e-4 |

Сначала учатся только новые случайные параметры: если сразу включить LoRA, их шумные градиенты испортят
предобученную Qwen.

Оптимизатор AdamW (weight decay 0.01; у τ, bias и норм — 0), warmup 3% шагов этапа, затем косинус; batch 128,
clip grad 1.0. Qwen в bf16, головы башен и логиты — в fp32 (при τ = 0.05 и softmax по 64k классам точности bf16 не
хватает). Gradient checkpointing. Валидация каждые 500 шагов, лучшая модель — по recall@100.

**Сколько обучается:** ≈5.6M новых параметров (из них ~3.2M — таблица тегов, ~0.8M — таблица кодов) + 4.6M LoRA.
Сама Qwen (0.6B) заморожена.

## Инференс

`scripts/encode_twotower.py` сохраняет `item_vectors.npy` (64016 × 256) и векторы запросов по частям датасета
(`query_vectors_<часть>.npz`, float16). Кандген в пайплайне (`recsys/candgen/dense.py`) просто ищет top-K по
скалярному произведению. Для новых запросов онлайн (`online: true`) запрос кодирует сама модель.
