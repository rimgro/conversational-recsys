# Lazy two-tower: память истории + cross-attention в Qwen

Ветка `dev/lazy`, код — `recsys/twotower/lazy.py` (`LazyTwoTower`, `LazyUserTower`, `TrackEncoder`,
`CrossAttention`), конфиг — `configs/lazy.yaml` (`arch: lazy`). В пайплайне `dev/baseline` — кандген
`twotower_lazy`, он читает готовые векторы из `artifacts/twotower/lazy_e0`. Схема: `docs/figures/twotower_lazy.svg`.
Эмбеддинги треков — [embeddings.md](embeddings.md).

## Идея: чем отличается от v2

В v2 ([twotower_v2.md](twotower_v2.md)) история стоит **в промпте**: 64 трека × 4 токена = 256 токенов, и все 28 слоёв
Qwen прогоняют их на каждый запрос. Это дорого, а длину истории ограничивает квадратичный attention.

В lazy история и запрос **разделены**, как в encoder-decoder (T5, Flamingo):

1. **История** → память `M`. Она зависит только от пользователя, её можно посчитать заранее и закэшировать.
2. **Qwen читает только текст запроса** (~34 токена) и через **cross-attention** перед каждым слоем смотрит в `M`.

Отсюда и название: историю обрабатываем «лениво», один раз на пользователя, а онлайн считаем только короткий запрос.
Ещё одно отличие: **трек = 1 токен** (в v2 было 4), поэтому в память помещается 256 треков вместо 64.

Цель эксперимента — понять, сколько стоит обработка истории и что она даёт: число слоёв энкодера `E` = 0, 2, 4 и
decoder-only бейзлайн `mode: prompt` (история в промпте, как в v2).

## Башня трека (`TrackEncoder`)

Три источника, каждый приводится к 256 и нормируется:

```
коды RQ-VAE c1..c4  → 4 строки СВОЕЙ таблицы (777 × 32, старт — центроиды RQ-VAE)
                    → склейка [128] → MLP 128→256 → GELU → 256 → LayerNorm                 [256]
теги                → TagTable: взвешенная сумма эмбеддингов тегов (~12.5k × 256) → LayerNorm [256]
название            → «артист — название», вектор Qwen3-Embedding [1024], посчитан заранее и заморожен
                    → Linear 1024→256 → LayerNorm                                         [256]
склейка                                                                                   [768]
   → MLP 768→512 → GELU → 512→256                                                   = r_j   [256]
   → Linear 256→256 → L2                                                            = v_j   [256]  кандидат
```

По сравнению с v2:
- коды **склеиваются**, а не усредняются, поэтому позиция кода не теряется;
- добавлено **название трека** как текст: Qwen знает многих артистов, и это знание помогает с запросами вида
  «что-то как у Radiohead»;
- таблица кодов **своя** (32-мерная, как в v1): общей с входом Qwen она быть не может, потому что вход теперь
  строится из `r_j`.

`r_j` всех 64 016 треков считается **один раз за шаг** и используется дважды: для токенов истории и для кандидатов.

## Башня пользователя (`LazyUserTower`, mode: encdec)

### 1. Токены истории

**Какие треки:** 256 уникальных треков с наибольшей суммой `exp(−давность / 180 дней)` по всем прослушиваниям, то есть
одновременно часто и недавно слушаемые (как в кандгене `history`). Порядок — по времени последнего прослушивания. Для
сравнения: цель есть среди последних 64 уникальных треков в 21.7% запросов train, а среди 256 по затуханию — в 45.6%.

```
токен трека j = LayerNorm( Linear 256→1024 (r_j)
                         + E_pos[место по свежести: 0 — самый свежий]        (256 × 1024)
                         + E_count[⌊log₂ числа прослушиваний⌋]               (16 × 1024)
                         + E_age[⌊log₂ (дней с последнего прослушивания + 1)⌋] (16 × 1024) )      [1024]
```
LayerNorm масштабирован так, чтобы норма токена совпадала со средней нормой обычных токенов Qwen.

### 2. Энкодер (E слоёв, по умолчанию E = 0)

- **E > 0:** копии первых E слоёв Qwen (обучаются целиком), attention **в обе стороны** (история — множество,
  causal-маска не нужна), RoPE по порядку истории, финальная RMSNorm.
- **E = 0:** энкодера нет, память — сами токены истории (вариант `lazy_e0`).

Память: `M = [пустой слот; выход энкодера]`, размер (1 + L) × 1024. Пустой слот — обучаемый вектор «ничего из
истории». Без него при пустой истории softmax в cross-attention берётся по пустому множеству и даёт NaN.

### 3. Декодер — Qwen по тексту запроса

Вход — только текст:
```
Instruct: Given a user's listening history and a request, retrieve the music track the user wants
Query: <текст запроса> <EOS>
```
Перед **каждым** из 28 слоёв Qwen (`cross_every: 1`) стоит блок cross-attention:

```
x ← x + tanh(g_l) · CrossAttn_l( q = RMSNorm(x),  k, v = RMSNorm(M) )
затем обычный слой Qwen l: self-attention по тексту (causal, RoPE) + MLP
```

- Веса `q, k, v, o` блока и нормы голов — **копия self-attention слоя l** Qwen (16 голов q, 8 голов k/v по 128).
  Блок сразу «говорит на языке» этого слоя. RoPE нет: порядок истории уже закодирован в `E_pos`.
- **Гейт `g_l = 0` на старте** → tanh(0) = 0 → декодер в точности равен исходной Qwen. Модель сама решает, насколько
  открыть каждый гейт. Средний |tanh(g)| пишется в лог («гейт»). Тот же приём, что во Flamingo.
- Выход: `h` = скрытое состояние EOS после финальной нормы → `u = L2(Linear 1024→256 (h))`.

Короткого пути из v2 здесь **нет**: он обходит декодер и скрыл бы разницу между вариантами энкодера.

### Вариант mode: prompt (decoder-only бейзлайн)

Те же токены истории (1 токен на трек) ставятся в промпт **перед** текстом, дальше идут обычные 28 слоёв Qwen с
causal-маской. Encoder-decoder сравнивается именно с ним.

## Обучение

Лосс, данные, валидация, маска дублей песен — как в v2 ([twotower_v2.md](twotower_v2.md)): softmax по всем 64 016
трекам, τ обучается.

| группа параметров | размер | lr |
|---|---|---|
| башня трека, вход истории (Linear, E_pos/count/age), выход, τ, гейты, пустой слот | ~4.6M | `lr` 1e-3 (A) / 5e-4 (B) |
| копии слоёв Qwen: энкодер (15.7M на слой) и 28 блоков cross-attention (6.3M каждый, 176M всего) | 176M при E=0, +31M при E=2 | `lr_copied` 1e-4 — они уже обучены, большой lr их сломает |
| LoRA r=16 на q, k, v, o декодера | 4.6M | только этап B, 2e-4 |
| Qwen3-Embedding-0.6B | — | заморожена |

Этапы A (0.3 эпохи, без LoRA) и B (1.7 эпохи, с LoRA) — как в v2. Копии слоёв учатся на обоих этапах.

## Стоимость (forward, GFLOP на запрос; история 254 трека, текст 34 токена)

| вариант | энкодер | k/v памяти | запрос | **всего** | кэш на пользователя |
|---|---|---|---|---|---|
| encdec, E = 0, cross в каждом слое | 0 | 30 | 40 | **70** | 29 МБ |
| encdec, E = 2 | 17 | 30 | 40 | 87 | 29 МБ |
| encdec, E = 4 | 34 | 30 | 40 | 104 | 29 МБ |
| encdec, E = 0, cross в каждом 4-м слое | 0 | 7.5 | 33 | 40 | 7 МБ |
| prompt (decoder-only) | 241 | 0 | 32 | **273** | 29 МБ |

«Энкодер» и «k/v памяти» зависят только от пользователя. Если их кэшировать, онлайн остаётся только столбец «запрос».
Decoder-only тоже может кэшировать k/v истории. Но на обучении кэша нет, и пример encdec E = 0 стоит 70 GFLOP
против 273 у decoder-only с той же историей — **примерно в 4 раза дешевле**. Считает функция `lazy_flops`.
